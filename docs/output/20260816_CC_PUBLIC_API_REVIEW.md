## Единственная существенная находка: `process_batch` — не общий контракт

Из 42 классов `*Operation` собственный `process_batch` определяют 19.
Остальные 23 делятся на две **разные** группы, и это важно различать.

### Группа 1 — законно не имеют его (18)

`process_batch` отсутствует в иерархии вовсе: 14 операций профилирования,
3 операции метрик и сам `BaseOperation`.

**`BaseOperation` не объявляет `process_batch`.** Это ключевой факт: пакетное
преобразование — контракт *преобразующих* операций (`AnonymizationOperation`,
`TransformationOperation`), а не всех операций вообще. Профилирование и
метрики строк не переписывают, им пакетный контракт не нужен.

**Это исправляет формулировку из дорожной карты**, где я писал про
«обязательный метод базового класса». Обязателен он не в `BaseOperation`, а в
двух промежуточных базах. Область дефекта уже, чем я заявлял.

### Группа 2 — наследуют абстрактный метод, который бросает (5)

Вот настоящий дефект, и он **шире**, чем я нашёл раньше:

| Операция | Откуда наследует | Собственная реализация |
|---|---|---|
| `AttributeSuppressionOperation` | `AnonymizationOperation` | нет |
| `CellSuppressionOperation` | `AnonymizationOperation` | нет |
| `RecordSuppressionOperation` | `AnonymizationOperation` | нет |
| **`SplitByIDValuesOperation`** | `TransformationOperation` | нет |
| **`SplitFieldsOperation`** | `TransformationOperation` | нет |

Раньше я называл три операции подавления. **Их пять** — две операции
разделения из `transformations/splitting/` имеют тот же дефект, и обнаружились
только при обходе публичного API, а не при просмотре пакета `anonymization`.

Наследуемый метод бросает `FeatureNotImplementedError: Subclasses must
implement process_batch`. Следствие: эти пять операций вызываются **только**
через полный `execute()` с файловым I/O и не работают как преобразование в
памяти. Для библиотеки, которую встраивает мост BEST, это необъявленное
ограничение.

### Что это значит для заморозки

Решение Val — 1.0 замораживает API. Тогда выбор надо сделать **до** релиза,
потому что после него ни один из вариантов не будет доступен без слома
совместимости:

**Вариант А — реализовать.** Все пять получают `process_batch`.
Для подавления записей это нетривиально: батч не самодостаточен, удаление
строк меняет их число, и семантика «подавить в пределах батча» может
отличаться от «подавить по всему набору». Для `SplitFieldsOperation` вопрос
проще.

**Вариант Б — сузить контракт.** `process_batch` перестаёт быть абстрактным в
базах; операции, которые его не поддерживают, объявляют это явным атрибутом
класса (например `supports_batch: ClassVar[bool] = False`), а вызывающая
сторона проверяет флаг вместо ловли исключения.

**Рекомендую Б.** Он честен относительно того, что уже есть, не требует
изобретать спорную семантику пакетного подавления, и даёт мосту BEST
машинно-проверяемый признак вместо исключения. Вариант А остаётся возможным
после 1.0 — добавить реализацию там, где флаг `False`, совместимость не ломает.
Обратный переход (из А в Б) сломал бы.

## Мелкие замечания, не блокирующие

**Шесть классов не оканчиваются на `Operation`** — `RuleCode`,
`SchemaManager`, `TaskConfig`, `BaseTask`, `DataSource`, `OperationStatus`.
Это не операции, и имена корректны. Замечание только в том, что публичная
поверхность смешивает два слоя: операции и инфраструктуру их запуска. Для
пользователя это нормально, для документации стоит развести на две группы.

**`__version__` как строка в `__all__`** — обычная практика, оставить.

## Что проверить дополнительно перед заморозкой

Эта ревизия смотрела на `__all__`. Не проверено и требует отдельного захода:

1. **Сигнатуры конструкторов операций.** Заморозка API — это заморозка имён
   параметров, а не только имён классов. Сверка с `parameter_schema` каталога
   DSL дала бы механическую проверку.
2. **Формат артефактов.** Имена файлов в `task_dir` — такой же контракт для
   моста BEST, как и сигнатуры. Нигде не зафиксирован.
3. **Совместимость с мостом BEST.** `_bridge_impl/*` вызывает около 40
   операций; прогон моста против этой сборки — единственная настоящая проверка.

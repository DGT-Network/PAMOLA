**Дата:** 2026-08-16

**Основания:** `20260816_CC_REPO_AUDIT.md`, `20260816_CC_TEST_BASELINE.md`,

## 0. Главный тезис

**1.0 должен быть сжатием, а не расширением.**

CORE — самая объёмная сборка экосистемы (620 файлов, ~202 тыс. строк) и
одновременно самая слабо отражённая в контракте: сверка по репозиториям
показала, что в каталог DSL поднята примерно треть. Добавление операций при
таком соотношении увеличивает неописанную поверхность, а не ценность.

Из четырёх заданных вопросов три отвечаются «убрать/унифицировать» и один —
«не делать». Это не осторожность: у каждого пункта ниже есть измерение.

| Вопрос | Короткий ответ |
|---|---|
| 1. Что почистить | ~10 тыс. строк выносится или удаляется без потери функциональности |
| 2. Что добавить | **Ничего** до 1.0. Атаки — решить статус, а не наращивать |
| 3. Polars | **Нет.** Выигрыш локализован в строковых операциях; их чинит векторизация pandas |
| 4. Унификация | Прогресс — лучшее, что есть (41/44). Ломается `process_batch`. Визуализация — крупнейшая нетестируемая подсистема |

## 1. Что почистить в CORE

### 1.1 LLM-контур — вынести (решение Val от 16.08 уже принято)

`pamola_core/utils/nlp/llm/` — **12 файлов, 7 511 строк**.

Бенчмарк-документ ставил вопрос: «что делать с зависимостями CORE, если на
`utils/nlp/llm` ссылаются другие подпакеты — проверить перед выносом».
**Проверено. Ответ: ссылается ровно один модуль.**

```
pamola_core/utils/nlp/text_transformer.py  → импортирует llm.client, llm.config,
                                              llm.metrics, llm.processing, llm.prompt
```

А `text_transformer.py` (779 строк) **не импортируется ничем** — ноль
потребителей во всём дереве, включая тесты.

Единственная другая связь — типы исключений `LLMError`, `LLMConnectionError`,
`LLMGenerationError`, `LLMResponseError` в `errors/exceptions/nlp.py`, на
которые ссылается реестр кодов ошибок. Они самостоятельны и переносятся или
остаются по вкусу.

**Вывод: контур является листом дерева зависимостей.** Выносится целиком,
одним движением, ~8 290 строк, без каскада правок.

Открытым остаётся вопрос 1 из бенчмарк-документа — **куда**: в HHR, в отдельный
пакет `pamola-nlp`, или удалить из публикуемой сборки. И вопрос 3 — нужна ли
запись в ADR/DGF о том, что CORE не несёт LLM-зависимостей. Для библиотеки,
которая ставится клиентам из PyPI, отсутствие LLM-контура — это, вероятно,
требование поставки, а не внутреннее предпочтение, и тогда его надо
зафиксировать так, чтобы он не вернулся.

## 2. Какие операции добавить

### Рекомендация: до 1.0 — ни одной

Обоснование — из сверки по репозиториям, §5 и §10:

> «CORE — самая полная и зрелая по объёму библиотека, и одновременно самая
> слабо отражённая в контракте: контракт описывает только то, что поднято в
> BEST.»

Добавление операций при покрытии контрактом ~1/3 увеличивает именно тот разрыв,
который сверка называет проблемой П3 («реализация впереди контракта»).

### 2.1 Атаки — решить статус, а не наращивать

Сейчас существуют **три несведённых инвентаря** (проблема П1 сверки):

| Инвентарь | Записей |
|---|---|
| DSL `ATK-*` | 22 |
| REDTEAM `RT-*` | 45 |
| CORE `attacks/` | 10 файлов, 1 620 строк |

При этом ни одного общего идентификатора между DSL и REDTEAM. В CORE атаки
объявлены экспериментальными (`README`, `__init__.py`, начиная с `1.0.0.dev2`)
и **не экспортированы** как публичные операции — в `__all__` нет ни одного
`Attack*Operation`. Они используются изнутри `PrivacyMetricOperation`.

Развилка, и её надо закрыть до 1.0:

**A. Оставить внутренними.** Записать в README и ADR, что `pamola_core.attacks`
— внутренний модуль без гарантий совместимости, и явно исключить из публичного
API. Дёшево, честно, ничего не обещает.

**B. Поднять в первый класс.** Каждая атака получает 4-файловую схему,
экспорт, покрытие, запись в каталоге DSL. Это 10+ операций × полный цикл —
работа не на 1.0.

**Рекомендую A** для 1.0 и B как отдельное эпик-направление. Смешанное
состояние — «есть, но экспериментальное, и неясно, покрывает ли критерий
EDPB» — худший из трёх вариантов, потому что именно оно даёт два разных ответа
на вопрос о покрытии.

### 2.2 Метрики — ничего не добавлять, свести существующее

Публичных операций метрик три: `FidelityOperation`, `PrivacyMetricOperation`,
`UtilityMetricOperation`, под ними 18 модулей. PMF сверен: все заявленные
метрики (`singling_out_rate`, `cvpl_score`, DCR, NNDR, ε/δ и прочие) имеют
носителя. Реально отсутствующие (`ATK-RECON-001`, `ATK-GRAD-001`) помечены
`planned`/`epic-4+` во всех реестрах согласованно — то есть это честно
описанный пробел, а не расхождение.

Работа здесь — §1.3 (убрать дубль KS/KL), а не расширение.

### 2.3 Что действительно стоит добавить, но это не операция

Из бенчмарк-документа, §5 — **три независимых места упираются в отсутствие
управляемого источника иерархий**: `CategoricalGeneralizationOperation` в CORE
требует `external_dictionary_path`, `PRIV-K-001` в BEST падает с
`MissingHierarchyError` на категориальном QI, в каталоге DSL иерархия задаётся
только инлайном.

CORE здесь **впереди** — понятие внешнего словаря уже реализовано. Значит
задача не «добавить операцию», а «описать контрактом то, что есть», и вклад
CORE в неё — документация формата словаря, а не код.

## 3. Стоит ли оптимизировать CORE через polars

### Рекомендация: нет

Три аргумента, по убыванию веса.

**Аргумент 1: измеренный выигрыш локализован и объясняется не движком.**

Из бенчмарка, единственные три прямые пары:

| Операция | BEST (polars) | CORE (pandas) | Кто быстрее |
|---|---:|---:|---|
| `ANON-GEN-001` числовое обобщение | 1 062 | **93** | CORE в 11.4× |
| `ANON-MASK-001` полное маскирование | **1 173** | 1 809 | BEST в 1.5× |
| `ANON-MASK-002` частичное маскирование | **1 557** | 3 523 | BEST в 2.3× |

Числовой путь CORE **уже быстрее** — он на numpy. Отставание только на
строковых операциях, и бенчмарк прямо называет причину: «построчная обработка
строковых значений в pandas против векторизованных строковых выражений polars».

Построчный `.apply` — это не ограничение pandas, а способ его использования.
`pandas.Series.str` векторизован. Значительная часть разрыва 1.5–2.3×
закрывается переписыванием этих конкретных операций на `.str`-аксессор —
это правка нескольких файлов, а не смена движка в 620.

**Аргумент 2: у CORE уже три механизма параллелизма, а не ноль.**

| Механизм | Файлов упоминают |
|---|---|
| `use_dask` | 88 |
| `use_vectorization` | 73 |
| `joblib` | 25 |

В `base_anonymization_op.py` они выбираются последовательными ветками
(`L910` dask → `L945` vectorization → fallback). Polars стал бы **четвёртым**
путём в том же переключателе. Проблема CORE не в отсутствии быстрого движка,
а в наличии трёх недоизмеренных.

**Аргумент 3: pandas — это публичный контракт, а не деталь реализации.**

CORE принимает и возвращает `pandas.DataFrame` через `DataSource`. Именно на
этот контракт опирается мост BEST (`_bridge_impl/*`). Смена на polars — это
слом публичного API у самой границы 1.0, ровно тогда, когда 1.0 должен его
зафиксировать.

Сверка формулирует это как осознанную границу (проблема П6): «polars+память в
BEST против pandas+файлы в CORE». **Это не дефект, который надо чинить, а
разделение ролей.** BEST — вычислительный тракт в памяти; CORE — файловая
библиотека операций. Сближать их движки — значит стирать границу, которая
оправдывает существование двух продуктов.

### Что делать вместо

1. Векторизовать строковые операции на `.str` (маскирование — в первую
   очередь). Дёшево, измеримо, без слома API.
2. Свести три механизма параллелизма к одному с честным замером — сейчас
   неизвестно, какой из трёх когда выигрывает.
3. Замерить `execute()` против `execute()` end-to-end с файловым I/O
   (бенчмарк это прямо называет недостающим): архитектурная разница может
   оказаться больше алгоритмической, и тогда оптимизировать надо I/O.

## 4. Унификация, прогресс, визуализация

### 4.1 Отслеживание прогресса — самая унифицированная часть

| Показатель | Значение |
|---|---|
| Модулей операций | 44 |
| Используют `progress_tracker` | **41** |
| Ссылаются на `HierarchicalProgressTracker` | **43** |

Три исключения: `anonymization/noise/uniform_numeric_op.py`,
`anonymization/noise/uniform_temporal_op.py`,
`profiling/analyzers/longtext.py`.

Это хороший результат, и его надо не переделывать, а **закрепить**: добавить
тест, проверяющий, что каждая операция из `__all__` принимает и продвигает
`progress_tracker`. Три исключения при этом закроются сами.

### 4.2 Унификация операций ломается на `process_batch`

Это главный дефект единообразия, и он подтверждён с двух сторон.

Бенчмарк не смог измерить две операции подавления:
`FeatureNotImplementedError: Subclasses must implement process_batch`.

Проверка по дереву показывает, что дело хуже — **ни одна из трёх операций
подавления не реализует `process_batch`**:

| Операция | Что определено вместо |
|---|---|
| `suppression/attribute_op.py` | `_process_batch_dask` (L455) |
| `suppression/cell_op.py` | `_process_batch_dask` (L274) |
| `suppression/record_op.py` | `process_batch_for_suppression` (L1508) |

Остальные 10 из 13 операций анонимизации `process_batch` реализуют.

Следствие ровно то, что называет бенчмарк: эти операции работают **только**
через полный `execute()` с файловым чтением и записью отчётов, и не могут быть
вызваны как преобразование в памяти. Для библиотеки, которую предполагается
встраивать — а мост BEST именно встраивает — это необъявленное ограничение.

**Для 1.0 это обязательно к исправлению**, потому что 1.0 фиксирует контракт:
либо все операции поддерживают пакетный вызов, либо базовый класс перестаёт
объявлять его обязательным и ограничение документируется явно. Текущее
состояние — абстрактный метод, который три подкласса не реализуют, — это
обещание в базовом классе, не выполняемое реализациями.

### 4.3 Визуализация — развитая, но крупнейшая непроверенная подсистема

| Показатель | Значение |
|---|---|
| `utils/vis_helpers/` | 20 файлов, **11 492 строки** |
| `utils/visualization.py` (фасад) | 2 120 строк |
| Итого | **13 612 строк — 6.7 % кодовой базы** |
| Двойной бэкенд (plotly + matplotlib) | 16 из 20 файлов |
| Модулей, не упомянутых ни одним тестом | **13 из 20** |
| Экспортировано в публичный API | **одна** функция — `visualize_distribution_df` |

Не покрыты: `bar_plots`, `combined_charts`, `cor_matrix`, `cor_pair`,
`cor_utils`, `histograms`, `line_plots`, `network_diagram`, `pie_charts`,
`scatter_plots`, `spider_charts`, `venn_diagram`, `word_clouds`.

**Ответ на вопрос «достаточно ли развито ядро вывода графиков»: да, развито —
проблема ровно обратная.** 13.6 тыс. строк, реестр бэкендов (`registry.py`),
темы (`theme.py`), контекст (`context.py`), 17 типов графиков, два бэкенда.
По архитектуре это зрелая подсистема. Но:

- она тянет в обязательные зависимости `plotly`, `matplotlib`, `seaborn`,
  `kaleido`, `wordcloud`, `matplotlib-venn` — шесть пакетов ради вывода
  картинок в библиотеке анонимизации;
- две трети её не проверяется ничем;
- в публичном API из неё — одна функция, то есть 13.6 тыс. строк формально не
  являются поверхностью, но поставляются и поддерживаются.

**Рекомендация: не обновлять, а зафиксировать и укрыть.**

1. Не переписывать. Архитектура нормальная, переписывание не окупится.
2. Определиться с бэкендом по умолчанию. Двойной путь в 16 файлах — это
   двойное тестовое бремя при одном используемом пути.
3. Smoke-тесты на 13 непокрытых модулей: график строится, файл пишется,
   не падает на пустых и односимвольных данных. Не проверка пикселей.
4. При решении по F-03 (extras) — вынести всю графику в `[viz]`.
   Пользователю, которому нужно замаскировать колонку, не нужен `kaleido`.

## 7. Чего этот документ не рассматривает

- Синхронизацию HHR ↔ CORE (рекомендация P2.10 сверки). После выноса
  LLM-контура из CORE картина меняется, и решение по HHR стоит принимать
  после шага 4, а не до.
- Сведение `RT-*` ↔ `ATK-*` (P2.8 сверки) — это работа в REDTEAM и DSL,
  CORE в ней участвует только через Р-2.
- Нормативный слой DGF (P3 сверки).
- Производительность BEST — узкое место там сериализация выхода, к CORE
  отношения не имеет.

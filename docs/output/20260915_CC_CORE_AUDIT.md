## 0. Главный вывод

**Разрыв с BEST — не в отсутствующих операциях, а в трёх других местах.**

1. **Ключевые алгоритмы CORE существуют, работают и невидимы.** k-анонимность,
   l-разнообразие, t-близость, DP и весь набор атак — это обычные классы, а не
   `BaseOperation`, и ни один из них не в `__all__`. 19 операций BEST
   соответствуют коду, который у CORE уже есть. Работа здесь —
   **продвижение, а не разработка**.
2. **Метрики CORE местами не просто менее точны, а бессмысленны.** Три
   подтверждённых дефекта (произвольная колонка, независимое кодирование
   категорий, обратное направление обучения) дают числа, не связанные с тем,
   что они называют.
3. **Библиотека содержит дефекты, которые нельзя публиковать.** Ключ шифрования
   попадает на диск открытым текстом; короткие значения проходят маскирование
   немаскированными; `eval()` с полными builtins висит на экспортируемой
   операции.

Из 21 операции BEST, отсутствующей в CORE, **15 должны остаться отсутствующими**
по ADR-PC-01/05 — это runtime BEST, а не библиотека.

### Б-1. Ключ шифрования пишется на диск открытым текстом · ПРОВЕРЕНО

Цепочка полная и не перекрывается редакцией `SENSITIVE_KEYS`:

| Шаг | Место | Что происходит |
|---|---|---|
| 1 | `utils/ops/op_base.py:857` | `"encryption_key": self.encryption_key` кладётся в словарь параметров |
| 2 | `utils/helpers.py:328` | `build_base_cache()` вставляет словарь под ключом `"parameters"` без фильтрации |
| 3 | `utils/ops/op_cache.py:243` | `save_cache()` пишет всё это через `write_json` в `cache/` |

Вызывается из всех четырёх базовых классов: `base_anonymization_op.py:1866`,
`base_transformation_op.py:1322`, `base_generator_op.py:1556`,
`base_metrics_op.py`, плюс 14 профайлеров.

Дополнительно `base_transformation_op.py:1320` логирует тот же словарь целиком:
`self.logger.debug(f"Operation parameters for cache: {operation_params}")` — при
том что `op_base.py:504` ведёт список `sensitive_params` для редакции логов.
Два механизма редакции в одном файле, и ни один не покрывает путь кэша.

Вес этого дефекта не в самом факте, а в том, что **README рекламирует
противоположное поимённо**: `README.md:86` про `SENSITIVE_KEYS` и отдельно
«AES-256-GCM mapping encryption keys are **never** persisted to disk». Для
библиотеки анонимизации опубликованное обещание о гигиене секретов, которое
опровергается вторым путём в том же файле, — это конец оценки.

**Смежное:** `OperationConfig.SENSITIVE_KEYS` по умолчанию `frozenset()`
(`op_config.py:61`), и переопределён он **ровно в одном** классе конфигурации из
41 — `anonymization/schemas/mapping_op_core_schema.py:37`. Незащищены, среди
прочего, `fake_data/schemas/*_op_core_schema.py` (PRGN `key`, `context_salt`) и
`anonymization/schemas/hash_based_op_core_schema.py:80` (`salt_config.value`).
Дизайн инвертирован: opt-in денилист для параметра, который принимают все операции.

**Исправление:** редактировать значение в `_get_base_parameters()` (или класть
солёный дайджест — он сохраняет различимость ключа кэша, не сохраняя секрет);
убрать debug-лог; перенести базовый набор в `OperationConfig.SENSITIVE_KEYS`,
чтобы наследовался. Плюс регрессионный тест: прогнать по операции из каждого
семейства с `encryption_key="…"` и грепнуть весь `task_dir` на литерал.
**2–3 чел.-дня.**

### Б-2. `BaseTask` никогда не видит ошибку операции · ПРОВЕРЕНО

`OperationStatus` определён дважды: `utils/ops/op_result.py:46` (6 членов, тот,
что в `__all__`, тот, что несёт каждый `OperationResult`) и
`profiling/commons/data_types.py:67` (4 члена, другой класс `Enum`).

`utils/tasks/base_task.py:55` импортирует **профайлинговый** во время
исполнения; правильный импортируется строкой `:61`, но под `if TYPE_CHECKING`,
то есть в рантайме его нет. Дальше `base_task.py:820`:

```python
if result.status == OperationStatus.ERROR:
```

Слева член `op_result.OperationStatus`, справа член `data_types.OperationStatus`.
Члены разных классов `Enum` никогда не равны — проверено отдельным прогоном:
`A.ERROR == B.ERROR` → `False`.

Следствие: `continue_on_error=False` не работает, `self.error_info` не
заполняется, **`BaseTask.execute()` рапортует успех на упавшем конвейере**.
`BaseTask` — публичный API.

**Исправление:** удалить дубль в `profiling/commons/data_types.py`,
реэкспортировать из `op_result`, добавить регрессионный тест.
**0,5–1 чел.-день.** Лучшее отношение тяжести к трудозатратам во всём аудите.

### Б-3. Частичное маскирование отдаёт короткие значения в открытом виде · ПРОВЕРЕНО

`anonymization/masking/partial_masking_op.py:1116-1117`:

```python
if unmasked_prefix + unmasked_suffix >= value_len:
    return value  # nothing to mask
```

При типовой конфигурации `unmasked_prefix=2, unmasked_suffix=2` любое значение в
4 символа и короче возвращается **целиком открытым**: короткие почтовые индексы,
инициалы, трёхзначные коды, усечённые идентификаторы. Операция при этом
рапортует успех.

В BEST это структурно невозможно (`partial_masking_002.py:340-365`): бюджет
видимого ограничивается длиной самого значения, префикс имеет приоритет над
суффиксом, и `min_mask_length` символов маскируется всегда. **~15 строк, порт
прямой. 0,5 чел.-дня.**

### Б-4. `eval()` с полными builtins на экспортируемой операции · ПРОВЕРЕНО

`transformations/field_ops/add_modify_fields.py:553-571` берёт `expression` из

операции, фиксированный список функций), значения связывать как имена, а не
подставлять в строку. **3–5 чел.-дней.** Если не успевает в релиз — закрыть

## 4. Ось II — качество пересекающихся операций

Сравнены 12 пар построчно. Ниже только то, где BEST объективно лучше.

### 4.1 Метрики — самые тяжёлые дефекты во всём аудите

Три из них ПРОВЕРЕНЫ лично. Каждый делает метрику не менее точной, а **не
связанной с тем, что она называет**.

| Дефект | Место | Следствие |
|---|---|---|
| `col = columns[0]` после `list(set(a) & set(b))` | `metrics/fidelity/distribution/kl_divergence.py:127`, то же в `ks_test.py:112-116` | Fidelity всего датасета сводится к одной произвольной колонке. Хуже: хеширование строк в CPython рандомизировано по процессам, **то есть колонка меняется между запусками** — метрика невоспроизводима |
| `OrdinalEncoder` фитится независимо на каждом фрейме | `metrics/commons/preprocessing.py:94-95`, вызовы `metrics/privacy/distance.py:137-138` | Одна категория получает разные коды в оригинале и в трансформе. DCR / NNDR / Uniqueness считают арифметику по несвязанным индексам меток. Любая категориальная колонка ломает все три |
| `X_train, X_test = X_original_train, X_transformed_test` | `metrics/utility/classification.py:190`, то же в `regression.py:227-229` | Это Train-on-Real / Test-on-Synthetic. Стандарт для оценки полезности релиза — обратный (TSTR). И нет потолка TRTR, поэтому абсолютный AUC нечитаем: 0,72 может быть и отличным, и провальным |

Дополнительно, не проверялось мной построчно, но с точным адресом:

- **Нет биннинга для непрерывных данных.** `kl_divergence.py:191-216` строит
  распределения через `value_counts()` для любого dtype. На непрерывной колонке
  каждое значение уникально → KL бессмыслен. BEST биннит на **общих границах**,
  посчитанных по объединению обоих наборов — иначе две гистограммы вообще
  несопоставимы.
- **Константа сглаживания абсолютная и большая.** `epsilon = 0.01`
  (`kl_divergence.py:78`) применяется до перенормировки. На 1000 категорий один
  только пол из epsilon даёт сумму ≥ 10, то есть настоящие вероятности
  сжимаются к равномерной примерно в 10 раз и KL систематически занижается.
- **Оценка риска тавтологична.** `metrics/privacy/distance.py:167-176` берёт
  пороги как процентили **того самого распределения DCR, которое оценивает**,
  поэтому `high_risk` всегда ≈5% записей, а `proportion_at_risk` всегда ≈0,05 —
  независимо от того, запомнила ли синтетика оригинал или это чистый шум.
- **Набор метрик.** CORE: KL + KS (`fidelity_ops.py:59-62`). BEST: KL, KS, JS,
  TVD, Wasserstein, CorrelationDelta. JS в CORE **уже написан**, но недосягаем
  из операции (TD-PC-16).

Идеи BEST, которые стоит забрать помимо исправлений: защита от вырожденного
словаря (TVD и категориальный JS упираются в потолок, когда носители
распределений не пересекаются — а обобщение **заменяет алфавит**, поэтому
расстояние читается максимальным для любого обобщения вообще); нормировка
Wasserstein на σ; базовая линия по холдауту для DCR/NNDR с явной пометкой,
настоящий это холдаут или расщепление.

**~12 чел.-дней на исправления + ~5 на расширение набора метрик.**

### 4.2 Параметры считаются по чанкам, а не по колонке

`chunk_size = 10000` — значение по умолчанию (`op_base.py:177`), и всё идёт через
`process_dataframe_using_chunk` (`base_anonymization_op.py:1006-1030`). Поэтому
любая стратегия, выводящая параметры из данных внутри `process_batch`, выводит
их **по-разному для каждого чанка**:

- `generalization/numeric_op.py:846-870` — min/max и квантили по чанку, то есть
  файл на 100 тыс. строк получает 10 разных схем биннинга, склеенных в одну колонку;
- `generalization/categorical_op.py:841-846` — частоты редких категорий по чанку.
  Значение, глобально редкое, но сконцентрированное в одном чанке, **выживает
  необобщённым**. Это отказ приватности, а не только несогласованность;
- `generalization/datetime_op.py:890-893` — опорная дата по чанку.

Правильный образец в CORE уже есть: `suppression/cell_op.py:713-725` строит
**глобальную** маску по всему фрейму до чанкинга. **3,5 чел.-дня на перенос
этой формы в три операции обобщения.**

### 4.3 Шум невоспроизводим, два параметра мертвы · ПРОВЕРЕНО

`anonymization/noise/uniform_numeric_op.py:272-278`: генератор присваивается
**локальной** переменной, `self._generator` (инициализирован `None` на `:190`)
никогда не записывается. Генератор пересоздаётся на каждый вызов
`process_batch`, то есть на каждые 10 тыс. строк. При
`use_secure_random=False, random_seed=42` **каждый чанк получает идентичный
вектор шума** — знающий 10 тыс. открытых значений восстанавливает шум,
применённый ко всему остальному файлу. Тот же дефект в
`uniform_temporal_op.py:349-355`.

Тем же способом мертвы `scale_by_std` и `scale_factor`: `:421` пишет в локальную
`_scale_factor_calculated`, а `_generate_noise` читает атрибут, который остался
`None`. Оба документированных параметра не влияют на вывод.

**0,5 чел.-дня + обязательный регрессионный тест, что шум различается на границе
чанков при фиксированном сиде.**

### 4.4 Подавление записей: у CORE нет самодостаточной k-анонимности

`suppression/record_op.py:838-890` — условия `null | value | range | risk |
custom`. Ветка `risk` только сравнивает с порогом **заранее посчитанное** поле
`ka_risk_field`, то есть требует отдельного прогона профайлера. CORE **не умеет**
сгруппировать по квази-идентификаторам и удалить классы меньше k.

BEST умеет, и несёт три предохранителя, которых у CORE нет вовсе:

1. **Отказ на прямом идентификаторе** — если у заявленного QI
   `n_unique == len(df)`, каждая строка сама себе класс и k-анонимность удалит
   весь датасет; операция отказывается и отправляет пользователя к подавлению
   атрибута или псевдонимизации;
2. **Пол по пустому результату** — удаление всех строк запрещено безусловно,
   независимо от потолка;
3. **Потолок `max_suppression_rate`** (по умолчанию 0,05). У CORE бюджета
   подавления нет вообще: `record_op.py:974-986` считает `suppression_rate` и
   только **логирует** его.

**4 чел.-дня.**

### 4.5 Прочее из списка портирования

`k_anonymity_by_level` для категориального обобщения (таблица достижимого k по
каждому уровню иерархии — выбор уровня и есть рычаг k-анонимности, а сейчас его
приходится искать перебором прогонов) — 2 дня. `match_policy` и
`ambiguity_policy` — 2 дня. Явные границы бинов, метки, артефакт с отображением

Сидирование ГПСЧ маскирования (`full_masking_op.py:1010-1018`,
`partial_masking_op.py:967`, `masking_patterns.py:584` используют глобальный
`random` без сида) — 1 день.

Полный список — 19 пунктов, **~40 чел.-дней**, из них ~9 — исправления ошибок.

## 6. Где CORE сильнее BEST

Это не пробелы, это дифференциаторы. Их не надо трогать, и их надо назвать в
позиционировании.

- **Псевдонимизация криптографически сильнее:** SHA3-256/512, соль из параметра
  или из файла солей с версионированием, сессионный перец в `SecureBytes` с
  автоочисткой, **отказ на слабой соли**, пол `output_length ≥ 8`, пять кодировок
  вывода, ключ кэша с сессией. У BEST — HMAC-SHA256 и `prefix`.
- **Хранилище отображений:** обязательный ключ шифрования, зашифрованный
  персистентный файл, восстановление счётчика между прогонами, обратный поиск,
  экспорт. BEST пишет отображение **незашифрованным**. И порядок присвоения в
  BEST хуже: он сортирует значения перед нумерацией, поэтому `ID-1 < ID-2`
  выдаёт алфавитный ранг оригиналов — **это не портировать**.
- **Маскирование:** библиотека пресетов на 1 495 строк, сохранение формата и
  разделителей, границы слов, согласованность между полями.
- **Даты:** шесть стратегий против одной у BEST (округление, биннинг с
  бизнес-периодами и сезонами, компоненты, относительные), часовые пояса.
- **Подавление ячеек:** импутация (mean/median/mode/group_*), детекция выбросов
  по IQR и z-score. И это **единственная операция, строящая глобальную маску до
  чанкинга** — образец для §4.2.
- **Реестр операций богаче BEST:** проверка зависимостей, ограничения semver,
  ленивая загрузка, обнаружение через `pkgutil`. Плюс CLI (`list_ops`, `run`,
  `schema`, `validate`), которого у BEST нет.
- **Атаки:** singling-out с SUDA, DIS-риском и интервалами Уилсона — богаче, чем
  у BEST.
- **Структурные мультиполевые условия** (`op_field_utils.py:811-851`) —
  инъекционно-безопасны по построению. У BEST на этом месте сырой SQL-фрагмент
  с трёхслойным аллоулистом, который пришлось прикручивать. **Не портировать.**
- Режим ENRICH с префиксом колонки, артефакты визуализации на операцию,
  кэширование, шифрование вывода — всего этого у операций BEST нет.

направление после.** Порядок внутри важен: блоки 0 и 2 независимы и дешёвы,

жизненного цикла, пока 30% файлов, которых она касается, намечены к удалению.

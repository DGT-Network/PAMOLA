# ADR-CORE-001: Dependency pins in published metadata, and the optional extras

| | |
|---|---|
| Status | **Proposed** (recommendation for after 1.0; nothing in this ADR changes the 1.0 metadata) |
| Date | 2026-10-23 |
| Scope | `pyproject.toml` `[project] dependencies` and `[project.optional-dependencies]`; CI installation; extras `nlp` / `bigdata` |
| Origin | Handoff task F3 ("do not mass-convert all 37 pins in the same stabilization effort; create a follow-up recommendation/ADR") |
| Related | DEVLOG `TD-PC-03` (hard-pinned runtime dependencies), `Q-03` (split pins into core + extras), SRS v1.1 sections 12.3, 12.4, 12.5, 8.7 |

## 1. Context

**What is published.** Every direct runtime dependency of `pamola-core` is declared with an exact
`==` pin in the wheel metadata (`Requires-Dist: pandas==2.2.2`, `numpy==1.26.4`,
`scikit-learn==1.7.2`, `scipy==1.15.3`, `dask[complete]==2025.11.0`, `spacy==3.8.9`,
`pyarrow==23.0.1`, ...). The ground-truth audit (2026-09-28, section 5) counted 37 direct pins;
after `pydantic[email]` was removed (DEP-01) there are **36** in `dependencies`, plus exact pins in
the `viz` extra (7) and `test` extra (`pytest==8.4.2`). The pins are historical only: they were
introduced by one mechanical mass commit with no per-package rationale (`git log -S`; DEVLOG
`TD-PC-03`, open question `Q-03`).

**What is missing.** There is no lock file and no constraints file anywhere in the repository. CI
(`ci.yml`, `release.yml`) installs straight from `pyproject.toml`, so the exact pins do double duty:
they are the only reproducibility mechanism for CI and, at the same time, the installability contract
imposed on every user of the library. Those are two different needs.

**Observed consequences.**
- *Resolver conflicts for users.* Installing the base package and any other library that needs a
  different `pandas`, `numpy`, `scikit-learn` or `cryptography` is unsatisfiable by construction. A
  library that pins its dependencies exactly can only be installed alone.
- *A concrete conflict inside the package.* The base install pulls `pillow-12.3.0` transitively
  (`dask[complete]` -> `distributed` -> `bokeh`), while the `viz` extra pins `pillow==11.3.0`;
  `pip install pamola-core[viz]` forces a downgrade or a resolver error (ground truth section 5).
- *Security fixes need a release.* A dependency CVE (for example the two `pyarrow` CVEs fixed in
  1.0 by moving to `23.0.1`) can only be taken by publishing a new `pamola-core`; users cannot
  upgrade the dependency themselves.
- *Support matrix is tied to the pins.* Python 3.13/3.14 fail today because the pinned versions of
  `pandas`, `pyarrow` and `fasttext-wheel` have no cp313 wheels (ground truth section 6/7); relaxing
  the pins is a precondition for widening `requires-python`.
- *Install footprint.* The base install is about 866 MB and 108 packages, mostly because heavy,
  already-optional packages (`spacy`, `nltk`, `fasttext-wheel`, `faiss-cpu`, `langdetect`) are
  mandatory (see section 7).

**Constraints for 1.0.** The stabilization scope (handoff F3) forbids converting the pins in the same
effort: every pin was tested together as a set, the 1.0 acceptance evidence (clean-wheel smoke,
`pip check`, `pip-audit`, Parquet round trip on Python 3.10/3.11/3.12) was produced against exactly
these versions, and there is no CI job yet that would prove a looser range works.

## 2. Options

**A. Keep exact pins.** Zero migration cost, maximal reproducibility of the installed set.
Downsides are those listed above; none of them gets better with time.

**B. Compatible-release pins (`~=`).** `pandas~=2.2.2` means `>=2.2.2,<2.3`. This removes patch-level
friction but still excludes the next minor release, so it does not solve the "cannot coexist with
other libraries" or the "Python 3.13" problems, and it still gives CI no reproducible set. It keeps
the same maintenance burden as A with a little less breakage; a half measure.

**C. Declared ranges with tested lower bounds, plus a generated constraints file for CI and releases.**
`pyproject.toml` declares what the code needs and was tested with (`pandas>=2.2.2,<3`,
`numpy>=1.26.4,<2`, ...). A constraints file, generated by a resolver from those ranges
(`pip-compile`/`uv pip compile`, per Python version), pins the full tree for CI, the release smoke
and the license/vulnerability reports. Users get a resolver-friendly library; maintainers keep an exact,
reviewable, reproducible environment; upgrades become a reviewed diff of the constraints file.

**D. Ranges only, no lock.** Smallest change, but CI becomes non-reproducible (a green run cannot be
repeated) and a transitive release can break the release pipeline on the day of the tag. Rejected.

## 3. Decision (recommendation)

Adopt **option C** after 1.0:

1. The library declares **ranges with tested lower bounds** and an upper bound at the next major
   version (or the next minor for packages that break on minors: `dask`, `distributed`, `pandas`).
   Lower bounds are not guesses: a CI job installs the **lowest** allowed direct versions
   (`uv pip install --resolution lowest-direct`, or an equivalent) and runs the test suite and the
   clean-wheel smoke.
2. **CI and release use a generated constraints file** (one per supported Python version, committed
   under `constraints/`, regenerated by a script, never edited by hand). `pip install -c
   constraints/py311.txt .[test,viz]` replaces the current "install the exact pins". The exact set
   that was smoke-tested is therefore recorded with each release (attach the file to the release
   artifacts together with the license report that `ci.yml` already produces).
3. **Dependabot** (or an equivalent bot) opens PRs against the constraints file and `pyproject.toml`
   ranges; **`pip-audit` gates** the PR (the `supply-chain` job introduced for 1.0 already audits the
   environment the wheel installs into; it would audit the constraints-resolved environment as well).
   An upgrade that passes the full test matrix and the audit can be merged without a code change.
4. Extras are fixed in the same step (section 6) so the `pillow` conflict disappears with the move
   from `==` to a range (`pillow>=11.3,<13` in `viz`).

## 4. Migration plan (post-1.0)

1. **Baseline.** From the 1.0 tag, generate `constraints/py310.txt`, `py311.txt`, `py312.txt` from the
   current exact pins (so the first constraints file reproduces 1.0 exactly). Switch CI and
   `release.yml` to install with `-c`. No range changes yet. Exit criterion: all workflows green on the
   same resolved set as 1.0.
2. **Lowest-direct job.** Add the lowest-direct install to CI as a non-required job; fix whatever
   fails by raising a lower bound or fixing a compatibility defect. Exit criterion: green on Linux
   with Python 3.10 and 3.12.
3. **Loosen in small groups, one PR each**, in order of lowest risk: pure utilities (`tqdm`, `rich`,
   `jinja2`, `packaging`, `filelock`, `joblib`, `PyYAML`, `chardet`, `psutil`, `cachetools`,
   `python-dotenv`, `jsonschema`, `base58`, `regex`), then I/O (`openpyxl`, `xlrd`, `ijson`,
   `pyarrow` - keep the security floor `>=23.0.1`, enforced by `tests/test_dependency_security_floor.py`),
   then the numerical stack (`numpy`, `scipy`, `scikit-learn`, `pandas` - each needs the full matrix),
   then `dask[complete]`, then NLP packages. `cryptography` gets a range with a floor at the version
   that carries the AES-GCM API the mapping storage relies on.
4. **Add Dependabot and the audit gate** (`pip-audit` on the constraints-resolved environment) before
   step 3 finishes, so each loosened group is audited on merge.
5. **Python 3.13**: with the ranges in place, re-run the clean-wheel smoke in a 3.13 container (the
   ground-truth test) and widen `requires-python` and the classifiers only if it passes.
6. **Document** the policy in `CONTRIBUTING.md`: how to regenerate constraints, how to raise a lower
   bound, who reviews dependency PRs.

Each step is reversible by reverting its PR and does not change the public API.

## 5. What 1.0 ships

- **Exact pins are kept** for all 36 direct dependencies and for the `viz` and `test` extras, exactly
  as in the release candidate that the acceptance evidence was produced against.
- Already done for 1.0 and unaffected by this ADR: `pyarrow==23.0.1` (security floor, test-enforced),
  `pydantic[email]` and eight other unused packages removed, `requirements.txt` removed, a
  `supply-chain` CI job (`pip-audit` on the installed wheel and a license report artifact).
- Known and accepted for 1.0: the library cannot coexist with applications that pin other versions of
  the same packages; the base install stays heavy; the `pillow` conflict between the base install and
  `[viz]` remains until step 3 of the migration. This is recorded in the as-built specification
  (`asbuilt/60_package_and_release.md`, SRS 12.4/12.5 divergences) and in the 1.0 release notes.

### Security-driven exception to the pin policy (SEC-DEPS)

Exact pins are kept, but where `pip-audit` on the installed wheel reports a fixable advisory the pin is
moved to the lowest release that fixes all fixable advisories, ahead of "pin stability":
`cryptography` 46.0.3 -> 50.0.0 (13 advisories), `nltk` 3.9.2 -> 3.10.3, `dask[complete]` 2025.11.0 ->
2026.1.1 (brings `distributed` 2026.1.1; 2026.1.0 itself requires dask 2025.12.x), `filelock` 3.32.3 ->
4.2.1 (Python >= 3.11 only; Python 3.10 stays on 4.1.0, the newest release it can install, which still
carries three filelock advisories - the CI audit runs on 3.11). The one advisory with no upstream fix
(nltk PYSEC-2026-3740) is listed in `.github/pip-audit-ignore.txt`, with a reachability analysis in
`.github/pip-audit-ignore.md`. This is an exception made for security, not a change of policy: the
post-1.0 ranges plus generated constraints (section 4) remain the way to stop doing this by hand.

## 6. Extras `nlp` and `bigdata` (post-1.0 item)

The base install is dominated by packages that the code already treats as optional. The audit measured
them by **actually uninstalling each and running the import and operation paths**:

| Package | Result at measurement time | Proposed extra |
|---|---|---|
| `spacy` | guarded by `try/except`, graceful degradation, zero code changes | `nlp` |
| `nltk` | guarded, zero code changes | `nlp` |
| `langdetect` | guarded, zero code changes | `nlp` |
| `fasttext-wheel` | guarded, zero code changes | `nlp` |
| `faiss-cpu` | guarded, zero code changes; **but** the scalable DCR path uses it | `bigdata` - only if a replacement path for DCR is approved (handoff F2 forbids moving it otherwise) |
| `pyarrow` | guarded | `bigdata` - with the security floor `>=23.0.1`; Parquet I/O must then say clearly that it needs the extra |
| `dask[complete]` | imported at module scope in `BaseOperation` and about 20 other files; **not** movable without a refactor | stays in base (separate refactor) |

Caveats to re-check before acting, because the code changed during 1.0 stabilization: the offline
policy (`utils/nlp/remote_resources`) and the per-run degraded-resource report now route most NLP
behavior; `utils/nlp/tokenization.py` initializes stemmers/lemmatizers at import time (a cost in
itself, independent of the extra split); and the clean-wheel smoke must be run on a base install
**without** the extras to prove that the degraded paths still work. The change is safe to make only
after the lowest-direct and constraints infrastructure exists, because moving a package out of the
base set changes what CI installs.

Proposed shape: `pamola-core` (core + `dask`), `pamola-core[nlp]`, `pamola-core[bigdata]`,
`pamola-core[viz]`, `pamola-core[all]`. Estimated effect (to be re-measured): the base install loses the
NLP stack and approaches the 300 MB internal target only together with the `dask` refactor.

## 7. Consequences

- Positive: users can coexist with other libraries; security upgrades no longer wait for a
  `pamola-core` release; Python 3.13+ becomes reachable; CI is reproducible by construction.
- Negative: a range can admit a version the project has not tested; this is mitigated by the
  lowest-direct job, the constraints-resolved matrix, and the audit gate, and must be monitored.
- Operational: someone owns dependency PRs; regeneration of constraints becomes part of the release
  routine.

## 8. Open questions

1. Owner and cadence of dependency updates (the DEVLOG `Q-03` owner question is still open).
2. Which resolver to standardize on (`pip-tools` or `uv`).
3. Whether `bigdata` should exist before a replacement path for DCR makes `faiss-cpu` optional.
4. Whether the consistent upper bounds (`<3` for pandas, `<2` for numpy) should be capped at the next
   minor until each major is tested.
